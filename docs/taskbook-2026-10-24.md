## 多用户 API Key、用量与计费管理服务

### 背景与目标

一个共享 API_KEY 只能回答“请求是否知道这串密钥”，无法区分是谁调用、花了多少、额度是否足够，也无法只撤销某个用户的访问。你需要把模型服务交付成一个可供多个用户或 Agent 使用的小型模型 API 平台：推理网关之外，还要有自己的管理服务、管理网页和持久化账本。

此处有两个不同的 token：

- API Key / access token：调用凭据。客户端在 `Authorization: Bearer <key>` 中提交，用来确定用户、权限和额度。
- 模型 token：模型处理的输入/输出文本单位。它们是用量与计费依据，不是访问凭据。

本项目要求多用户 API 的凭据和用量能力，不要求复制某个商业产品的订阅模式。第一期实现内部余额、计费与账单，不要求真实收款、信用卡、税务或支付渠道；界面明确标注“实验账本”，不能把它与平台租用 Daytona 的真实预算混为一谈。

### 必须交付的管理网页与后台

管理网页入口为 `GET /console`，可使用简单 HTML 或任意前端框架；必须连接真实管理 API 和持久化数据库，不能只有截图、mock 页面或直接编辑 JSON 文件。至少完成以下操作：

| 模块 | 必须实现 | 完成标准 |
| --- | --- | --- |
| 用户/租户 | 创建、列出、停用用户，设置余额和请求额度；最少 Alice、Bob 两个独立用户 | 同一模型服务中两个用户的用量、额度、账单互不混淆 |
| 密钥管理 | 同一用户多把 key；创建、命名、查看状态/到期时间、轮换 rotate、撤销 revoke | 原文仅创建/轮换时展示一次；列表只有 key_id、前缀/尾号和状态 |
| 权限隔离 | 管理员凭据与推理 key 分离；普通 key 只能推理和读取自己的使用情况 | A 的 key 不能查看 B 的账单、创建用户、充值或调用引擎管理接口 |
| 用量统计 | 按用户、key、模型、日期统计请求数、输入/输出 tokens、失败/取消数 | 同时保存逐请求账本和汇总，汇总可与明细对账 |
| 定价与账单 | 输入与输出 token 单价分别配置；每条账目保存价格版本和金额 | 正常流式与非流式均按真实用量结算；更新价格不重算历史账目 |
| 额度与限流 | 用户余额、累计 token 上限、RPM、并发上限；余额不足在进入引擎前拒绝 | 多请求并发不会透支；限流不能通过多建一把 key 绕过用户级总限额 |
| 审计与持久化 | 创建/轮换/撤销/充值操作审计；进程重启后保留用户、key 摘要、余额与账单 | setup.sh 幂等重跑不清空数据库；日志不出现完整密钥 |

RPM 是 Requests Per Minute（每分钟请求数），与同时在途的并发数不同。普通推理调用自动识别身份，不让客户端用 `user_id`、`tenant_id` 或 `role` 指定计费归属。

密钥使用密码学安全随机数生成（至少 32 个随机字节），数据库保存校验摘要，不保存可回读的原文；可使用 HMAC-SHA256，并把服务端 pepper 放在独立私密环境变量中。不能把 pepper、管理员凭据、已签发 key 放入 GitHub、前端构建产物、URL 或日志。若使用管理员网页登录会话，设置安全 Cookie、过期时间并保护写操作免受 CSRF；普通 key 不得获得管理能力。

### 请求与计费实现流程

```text
Agent 携带自己的 API Key
  → 网关校验 key 状态/有效期 → 服务端确定 tenant_id + key_id
  → 检查用户状态、RPM、并发、余额、token 上限
  → 数据库事务：创建请求记录并预占最大允许费用/用量
  → 提交给 SGLang（仍使用同一个请求 ID）
  → 非流式或 SSE 输出；从引擎记录实际 input/output tokens
  → 事务结算一次：扣实际金额、释放未使用预占、更新汇总
  → 管理网页展示账单；用户 API 只能返回自己的用量
```

使用可信引擎的 usage，输入包含实际 chat template；服务端计费不接受客户端提交的 `usage`、`cost` 或 `user_id`。即使客户端不请求 `stream_options.include_usage`，网关也必须自行取得计费数据。模型前缀缓存命中不代表用户输入 token 自动为零；第一版统一按输入/输出 token 价计费，cached_tokens 单独记录，不能暗中更换计价规则。性能评测中控制端的独立 tokenizer 复核是另一项验证，不等于允许客户端决定账单。

金额使用整数微美元（1 USD = 1,000,000 micro-USD）或精确 Decimal，不用二进制浮点累计余额。以下单价仅为确定性测试夹具，不是模型市场报价或真实收费承诺：输入每 token 2 micro-USD，输出每 token 6 micro-USD。

```text
cost_micro_usd = input_tokens × 2 + output_tokens × 6
例：输入 100、输出 50 → 100×2 + 50×6 = 500 micro-USD = 0.0005 USD
```

预占按已验证的输入 token 数和本次允许的 max_tokens 上限计算，成功后按实际用量结算并返还差额。余额检查与预占必须在同一个数据库事务中执行；不能先读余额、稍后异步扣费。SQLite WAL + 事务可满足本项目单机实现，不强制 Redis、外部数据库或微服务拆分；多进程部署时仍要验证事务与锁的边界。

每个请求使用服务端唯一 request_id；内部重试、重复结束事件不能重复扣费。对显式提供 `Idempotency-Key` 的生成请求，实现按租户、路由和请求体哈希去重：同 key 同请求不能重复推理或扣费；同 key 不同请求体返回 409。重复进行中的请求可返回 409 `request_in_progress`；已完成请求可返回已保存结果或 409 `request_already_completed` 和原 request_id，但不可悄悄再生成一次。未提供幂等键的独立调用按独立请求处理。

| 生命周期 | 账本与额度要求 |
| --- | --- |
| 鉴权失败、未进入引擎的拒绝 | 不扣模型费用，不产生已结算 token 用量 |
| 正常完成 | 按实际 input/output usage 结算一次，释放多余预占 |
| 客户端断开/超时 | 传播取消、关闭流；若取得可信实际 usage，按截止取消的实际用量结算 |
| 中断且未取得完整 usage | 标记 pending_reconciliation（待对账），保留已预占额度，不能伪造 0 token、默默收满上限或假装结算成功 |
| 重启恢复 | 扫描未完成账目，对已终止任务核对引擎证据；模拟故障测试在恢复后 60 秒内收敛，不能重复扣费或永久冻结余额 |
| 撤销/过期/轮换 | 操作完成后发起的新请求立即按新状态鉴权；已获准的在途请求可完成，按原用户和 key_id 记账，规则写入 README |

第一期统一采用零宽限期轮换：原子创建新 key、撤销旧 key；新 key 可用，旧 key 后续请求返回 401。正常会话中已获准请求的处理规则如上。恢复时若无法取得可信用量，必须保留失败证据并以可审计的 credit_adjustment 释放预占，记录未计费用量/金额状态为 unknown，不能把未知值写成真实 0；账本明确显示该次未完成精确计费。

### 固定接口合同 credential-service/1

所有管理 API 在同一个网关下提供，仅接受独立 ADMIN_API_KEY（或由它建立的管理会话）。普通 API Key 不得调用 `/admin/*`。创建资源返回 201，查询/轮换/撤销/调整余额成功返回 200；错误使用 `{"error":{"code":"...","message":"..."}}`，不泄露密钥。时间使用 UTC ISO 8601，金额/额度使用整数。

| 接口 | 请求与返回最小约定 |
| --- | --- |
| `POST /admin/tenants` | 输入 name、balance_micro_usd、token_limit、rpm_limit、concurrency_limit；返回 tenant_id 与设置 |
| `GET /admin/tenants` | 返回 items 数组，含 tenant_id、name、status、余额、已用与预占 tokens |
| `PATCH /admin/tenants/{tenant_id}` | 修改 status（active/disabled）和限额；余额由单独调整接口修改 |
| `POST /admin/tenants/{tenant_id}/credits` | 输入 delta_micro_usd、reason 与 Idempotency-Key；返回 adjustment_id 和余额；重复同请求不重复入账，不能扣出负可用余额 |
| `POST /admin/tenants/{tenant_id}/keys` | 输入 name、expires_at；返回 key_id、api_key（仅这一次）、status、expires_at |
| `GET /admin/tenants/{tenant_id}/keys` | 返回 items，含 key_id、masked_key、status、created_at、expires_at；禁止 api_key 原文 |
| `POST /admin/keys/{key_id}/rotate` | 输入 expires_at；返回新 key_id、api_key、replaced_key_id、旧 key 的 revoked 状态 |
| `POST /admin/keys/{key_id}/revoke` | 撤销，重复撤销幂等；返回 key_id、status=revoked |
| `GET /admin/usage?tenant_id=...&from=...&to=...` | 返回 summary 与按 cursor 分页的 items：request_id、route、parent_request_id（无父账时 null）、tenant_id、key_id、model、status、input_tokens、output_tokens、cost_micro_usd、pricing_version、时间；待对账字段为 null 并带状态 |
| `GET /admin/pricing` / `PUT /admin/pricing` | 读取/设置模型的 input_micro_usd_per_token、output_micro_usd_per_token；每次更新产生不可变 pricing_version |
| `GET /v1/usage` | 普通 key 读取服务端识别的自身用户 summary：balance_micro_usd、reserved_micro_usd、input_tokens、output_tokens、cost_micro_usd；不得接受其他用户 ID 越权查询；items 账目包含 route、parent_request_id（无父账时 null） |
| `GET /console` | 真实后台页面，提供上述用户、key、余额/配额、定价、账单与审计操作；无管理身份不返回敏感数据 |

不存在或不属于可访问范围的资源不能泄露内容。无效、过期或撤销的 key 返回 401；租户停用返回 403；余额或累计 token 额度不足返回 402 `insufficient_quota`；RPM/并发超限返回 429 并附 Retry-After。仅允许明确声明的可编辑字段，客户端不能写入 used_tokens、cost、key_hash 或管理员角色。

setup.sh 增加读取 `ADMIN_API_KEY`、`KEY_HASH_SECRET`、`DATA_DIR`；首次初始化迁移与管理员入口，缺少管理配置时管理接口关闭并给出清晰提示，不能采用公开默认密码。保持原 `API_KEY` 兼容：把它初始化为一个独立的 benchmark 用户推理 key，普通权限且仍走记账/限流，不作为管理员或“免计费后门”。压测时预置足够余额和限额，单独测试配额拒绝，不能让意外余额耗尽污染性能结果。

正常进程重启或同目录 setup 重跑必须保留 DATA_DIR；Daytona 沙箱销毁会清空本地数据。仓库保存迁移、schema 和合成 seed，不能把真实用户账本/凭据提交到公开仓库；新沙箱从代码重建服务，可通过脱敏数据验证恢复流程。

11. 调价前后生成两笔账单，分别使用各自价格版本；重复充值请求只入账一次；summary 与明细精确相等。

fixture 的 `POST /tokenize` 返回 `count=100`（并提供 token ID 数组）；推理返回受控的 `usage`：输入 100、输出 50。初始输入/输出价格分别为 **2 / 6 micro-USD/token**，一次费用为 `100×2+50×6=500 micro-USD`。fixture 可延迟响应、在 usage 前中断、或先发最终 usage 再延迟 `[DONE]`。这些确定性数据只用于事务验收，不用于性能分或真实模型正确性评分。 fixture 提供 `GET /health`、`GET /v1/models`、`POST /tokenize`、`POST /v1/chat/completions` 和 `POST /abort_request`（使用对应请求的 `rid`）。`/__fixture/*` 仅供控制端配置和观察，提交服务不能依赖这些管理接口或获取 fixture 管理凭据。

#### 与真实 SGLang 部署联合验收

15 项 CPU 确定性检查不是独立的模拟项目。每个 5 分组还必须通过对应的 **optimized 真实 GPU 服务部署检查**才保留该组 CPU 得分；对应部署检查失败或未完成，该组为 0，并标注“部署未验证”。原始 CPU case 结果仍保留用于定位问题，不把其通过状态改写成已获得最终组分。

真实服务检查会创建两个独立用户，分别完成流式和非流式调用，核对首个内容事件、流结束标记、实际 usage 与费用/用户账本及互不可见；测试轮换后旧 key 401、新 key 可调用；并确认原 `API_KEY` benchmark 用户的 `/v1/usage` 中已有真实模型调用账目。正式性能、正确性与 Agent 测试不能绕开鉴权、配额和账本。

#### 报告中的通过、失败与未执行

`report.checks` 的 `id="credentials"` 项上限 15，`subchecks` 三组为 `key_lifecycle`、`metering_billing`、`quota_recovery`，每组上限 5。`cases` 按上述 test_id 保存 `id/title/group/executed/passed/detail`，不包含原文 key。

`executed=true` 且 `passed=true` 才是该项通过；执行后断言失败显示未通过。`executed=false` 或缺少记录显示未执行/无记录，并列出原因。未实现 `--contract-test` 或提交服务启动失败属于未完成交付，可得 0/15，不会因显示未执行而自动免扣分；控制器自身异常或失租的报告由平台标明中断，不能据此声称正式验收通过。公开自测只产出本地证据，不能提交分数或代替控制端测试。

## 性能指标与达标规则总表

你交付的性能结果必须回答三个问题：每秒能提供多少有效输出 token、用户等待多久、在多少并发请求下仍然稳定。不能只提交 GPU 利用率截图、单个请求的速度或一个平均 token/s 数字。

### 固定测试条件

- 硬件：单张 Daytona RTX 4090；模型 Qwen/Qwen2.5-7B-Instruct，BF16，revision 以验收配置为准。

| 有效输出吞吐（Output Token Throughput） | token/s；正确且成功请求的实际输出 token 总数 ÷ 整组测量窗口秒数 | 越高越好；四组最低值以顶部“当前性能验收配置”为准 |
| TTFT（Time To First Token，首 token 延迟） | ms；发出请求至首个非空内容事件，报告 p50/p95；包含排队与网络 | 越低越好；四组 p95 上限以顶部“当前性能验收配置”为准 |
| TPOT（Time Per Output Token，平均每输出 token 时间） | ms/token；(最后内容时间−首个内容时间)/(实际输出 tokens−1)，报告 p50/p95；需多个内容事件和 N>1 | 越低越好；四组 p95 上限以顶部“当前性能验收配置”为准 |
| E2E（End-to-End Latency，端到端延迟） | ms；请求发出至完整响应结束，报告 p50/p95 | 越低越好；四组 p95 上限以顶部“当前性能验收配置”为准 |
| Goodput（满足质量与 SLO 的有效请求吞吐） | 请求/s；正确且成功、同时满足 TTFT/TPOT/E2E 上限的请求数 ÷ 测量窗口 | 越高越好；没有冻结 SLO 时不可计算验收 goodput |
| SLO 达标比例（Service Level Objective Attainment） | %；正确且成功且满足联合 SLO 的请求数 ÷ 全部请求数；失败也在分母中 | 四组最低比例以顶部“当前性能验收配置”为准，不单独生成分数 |
| 请求成功率（Success Rate） | %；正常完成协议的请求数 ÷ 全部请求数，429、超时、截断流均计失败 | 现行正确性项 ≥95%；正式性能目标每组 ≥99%（48 请求须 48/48）；标定/确认资格另要求 100% |
| 输出正确率（Quality Rate） | %；正确且成功请求数 ÷ 全部请求数，按固定任务核对答案 | 现行正确性项 ≥90%；正式性能目标每组 ≥99%（48 请求须 48/48）；标定/确认资格另要求 100% |
| 可持续并发（Sustainable Concurrency） | 同时在途请求数；测试档位中仍满足全部质量、吞吐与延迟门槛的最大 C | 必须测到 C=16；“发出了 16 个请求”不等于“并发 16 达标”；无门槛时不宣称可持续并发 |
| 显存与容量 | MiB/GiB；报告进程峰值显存、KV token 预算、active/queued 峰值；区分 allocated/reserved 与整卡占用 | 目标负载无 OOM；配额、队列有界；取消后请求与 KV 生命周期结束，不要求缓存内存池退还全部显存 |
| 部署与恢复 | 秒；首次 setup 就绪时间、幂等重跑、取消后恢复请求结果 | 安装就绪预算 ≤900 秒；同配置重跑不产生重复引擎；取消后能继续服务 |

p95 表示 95% 样本不超过该值。不要把所有并发/长短请求混成一个 p95 来掩盖某组失败。每组保留成功数、错误分类、原始到达时间、实际输出 tokens 和至少三轮记录；正式报告现有字段以 p95 为主，p50 可随工程压测结果提交。

“token 的并发量”应拆成 C（同时在途请求）、token/s（吞吐）和 KV token budget（缓存容量）三个量。ITL（Inter-Token Latency，相邻 token 间隔）只有真实逐 token 时间戳才能计算；SSE 事件间隔只作为块间隔诊断，不冒充 ITL。

## 性能验收工作负载

性能验收针对最终 HTTP 服务，不是只检查实验文件是否存在。平台固定 RTX 4090、Qwen/Qwen2.5-7B-Instruct revision `a09a35458c702b33eeacc393d103063234e8bc28`、BF16、上下文上限和负载版本。模型变小、换精度、缩短要求的输出或调用外部 API 都不属于合法优化。

平台比较 baseline 和 optimized，并记录每档并发的成功/失败、正确性、TTFT、E2E、TPOT、输出 token/s、goodput。服务接口、输出正确性和 Agent 项只验收最终 optimized 服务；正确性分母包含该服务全部测试请求及失败。baseline 是重建与性能负对照，失败仍保存，但不混入最终服务正确性分母。独立预热，不把预热请求算入计分窗口；保留超时和失败；共享前缀与不同前缀、冷缓存与热缓存分开记录。两种配置使用同一批测试输入。输出 token 数由控制端使用指定 tokenizer 对可见输出文本重新计数，不直接相信服务自报 usage；该数字不包含隐藏 token，也不假装是引擎内部 token 时间戳。

- **并发**：同时在途的请求数；不是 token/s。可持续并发是保持成功率、正确性和延迟 SLO 的最大测试档位。
- **输出吞吐 output token/s**：正确且成功的输出 token 数除以整个测量窗口。输入 token 不混入输出吞吐；全部成功输出吞吐另作诊断，不用错误答案换取速度分。
- **TTFT（Time To First Token）**：请求发出至第一个非空输出内容事件。
- **E2E（End-to-End Latency）**：请求发出至完整响应结束。
- **TPOT（Time Per Output Token）**：首个至最后输出内容事件时间除以输出 token 数减一，是每个请求的平均解码时间代理；不能替代逐 token 尾延迟。
- **ITL（Inter-Token Latency）**：相邻 token 的时间间隔。SSE 可合并多个 token，未记录独立 token 时间戳时，只能报告块间隔，不能标成 ITL。
- **SLO（Service Level Objective）**：例如 p95 TTFT 和 E2E 的明确上限。
- **Goodput**：单位时间内正确且同时满足 SLO 的请求数。输出很快但错误或超时的请求不计入。

### 硬指标配置与标定

Daytona 首轮从零验证完成后，平台发布冻结的 `acceptance.json`，包含 GPU、模型、工作负载、并发档位、请求数、输入/输出限制、最低输出 token/s 与 goodput、最高 p95 TTFT/TPOT/E2E、成功率和正确率，以及每项分数。报告保留该配置版本与实测值。

## 自动优化实验合同

平台完成服务和 Agent 测试后，在独立 GPU 上依次运行：

```bash
bash experiments/run.sh --case kv --out results/platform-<run-id>/kv
bash experiments/run.sh --case prefix --out results/platform-<run-id>/prefix
bash experiments/run.sh --case attention --out results/platform-<run-id>/attention
```

入口必须支持新的输出目录，在本次环境实际执行，不能复制已提交的结果冒充新测量。按实验用途读取模型配置与 HF_HOME：Prefix 使用服务的 MODEL_ID / MODEL_REVISION（7B），KV 使用下述独立固定的 1.5B 模型，Attention 仅生成合成张量；manifest 如实记录所用模型及实验用途。依赖由 setup.sh 安装；运行实验不临时升级环境。KV/Attention 最多各 300 秒，Prefix 最多 480 秒，并受完整评测总时限约束。实验可停止本项目服务以避免同时加载两份模型。

每项自动 10 分：执行溯源 2、矩阵覆盖 2、输入一致性 1、性能数据 1、数值/输出正确性 2、机制证据 2，逐项展示得分与理由。原理实验不要求固定加速倍数；最终服务的硬性能门槛另计入 30 分。平台不信任自报 points 或 summary.pass，也不把退出 0 当作正确性证明。

KV 数学等价性实验独立固定为 Qwen/Qwen2.5-1.5B-Instruct revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`，参考实验使用 FP32 并关闭 TF32，不加载 7B FP32。FP32 最大绝对误差 ≤0.001、top-1 一致率 100%；平台保留 BF16 对照兼容，最大绝对误差 ≤0.15、rtol=0.02、top-1 一致率 100%，不得因失败放宽容差。最终 SGLang 服务使用 7B BF16，不把 1.5B FP32 原理通过写成 7B BF16 logits 对照通过。

- KV：cache on/off × 长度 128/512 × 3 轮，共 12 条；固定回放 32 个 decode token。预热后 GPU 同步计时。相同输入与 continuation，比较逐位置 logits；记录峰值 allocated/reserved 和容量公式。BF16 最大绝对误差 ≤0.15、FP32 ≤0.001，top-1 一致率 100%，不事后放宽容差。
- Prefix：使用与最终服务相同的 7B BF16 模型及 revision；on/off × 共享/不同前缀 × 3 轮 × 8 请求，共 96 条。共享前缀 512 tokens，先清缓存再跑冷/热请求；保存输入 token IDs 和真实 cached_tokens。关闭时命中为 0，共享热请求 ≥512，冷/不同前缀 <512。原始输出必须正确，不以速度推断缓存命中。
- Attention：使用合成 Q/K/V 张量，不加载 7B 模型权重；math/flash × 长度 128/512/1024 × 3 轮，共 18 条；B=1,H=8,dh=64，BF16、causal、dropout=0，预热 5 次，每轮 10 次。相同 Q/K/V，最大绝对误差 ≤0.02，保存 profiler 算子。后端不支持应明确失败，不静默回退后宣称 flash。

数值失败仍保留完整数据并返回非零；中途失败标记 complete=false。源码、原始数据和 docs/performance.md 应可相互追溯。人工验收仍仅 5 分，不为这些实验另设人工分。

### 证据文件格式

每个 `--out` 目录必须生成 UTF-8 JSON 文件，不允许符号链接，每个被采集文件最多 256,000 字节；未完成字段写 null，禁止 NaN/Infinity。所有原始行的分组键必须唯一，缺失/重复/额外样本都会使矩阵检查失败。

`manifest.json`：`case`（kv/prefix/attention）、`time`（本次 UTC ISO 时间）、`commit`（完整 SHA）、`model`、`revision`、`gpu`（`nvidia-smi --query-gpu=name,uuid,driver_version,memory.total --format=csv,noheader` 原始文本去尾部换行）、`software`（torch/transformers/sglang 版本）、`cuda`、`complete`（只有完整运行才为 true）、`parameters`。数值不通过仍应保留 complete=true，并返回非零；中途失败为 false。

- KV parameters：lengths=[128,512]、decode_tokens=32、warmup≥1、repeats=3、dtype=bfloat16 或 float32。raw.jsonl 共 12 行：variant=cache_on/cache_off、length、repeat=0/1/2、input_hash、continuation_hash、decode_tokens、dtype、elapsed_ms、peak_allocated_bytes、peak_reserved_bytes、max_abs_error、atol、rtol、top1_agreement。同一长度的 prompt/continuation 哈希必须一致。summary.json：layers=28、KV_heads=2、head_dim=128、dtype_bytes（2/4）、KV_bytes_per_token；measurements 两项包含 length、KV_bytes_one_request、KV_bytes_eight_requests（包含额外 32 token）。逐位置比较 logits，记录全部位置最大误差；评分采用保守的最大绝对误差阈值，而不是采信自报 allclose。
- Attention parameters：warmup≥5、groups=3、iterations=10、dtype=bfloat16、causal=true、dropout=0。raw.jsonl 共 18 行：variant=math/flash、length、repeat、shape、output_shape、input_hashes（Q/K/V 三个 SHA256）、elapsed_ms、peak_allocated_bytes、peak_reserved_bytes、max_abs_error、atol=.02、rtol=.02。另存 math-128-operators.json、flash-128-operators.json 等三个长度共 6 个文件，内容是 profiler 算子名称字符串数组；保存完整 trace 供追溯。
- Prefix parameters：prefix_tokens=512、requests=8、repeats=3。raw.jsonl 共 96 行：variant=on/off、group=shared/unique、repeat=0/1/2、index=0…7、input_hash、prefix_hash、prefix_length=512、input_tokens、cached_tokens、cache_state、output、transport_ok、ttft_ms、e2e_ms。每轮 index=0 为 cold，开启缓存且共享前缀 index>0 为 hot。inputs.json 为 `{ "shared": [8个token ID数组], "unique": [8个token ID数组] }`；hash 使用 Python `sha256(json.dumps(value, sort_keys=True).encode()).hexdigest()`。每个 on/off、shared/unique、repeat 组合保存 `<variant>-<group>-<repeat>-flush.json`，至少包含 status=200。实际引擎命中计数来自服务结果，不能由速度推断。summary.json 保留各组窗口、成功率、质量 goodput；不得隐去零 goodput。

张量哈希使用连续张量原始字节的 SHA256；Prefix 使用上面的 JSON 序列化。保存原始失败记录及图表，docs/performance.md 链接同一 commit 的证据。未执行或格式错误的组不得显示“通过”。

## 候选阈值与独立确认

独立确认成功后，控制端可重新审计原始证据，另生成带完整确认凭据的 `finalized-report.json` 作为正式自动评分；原始 `report.json`、测量记录和历史临时报告不改写。仅将 provisional 改为 false 不能生效，页面还须核对确认凭据与当前运行和 commit 的绑定；人工验收仍仅 5 分。

标定数据资格与正式性能评分是两层要求：生成候选阈值和独立确认时，optimized 的 short/long × 并发 1/4/8/16 全部 8 组，以及 baseline 的 short/long × 并发 1 两组，必须每个测量请求都正确且成功（100%）；不能用其他组的高分抵消。正式性能评分目标为 optimized 的 short/long × 并发 8/16 四组，各组成功率与正确率均须 ≥99%。本期每组 3 轮 × 16 = 48 个测量请求，因此 ≥99% 实际要求 48/48 正确且成功（47/48 约为 97.92%，不达标）。baseline 的较高并发只允许已确认的容量失败，且每轮至少有 1 个正确成功样本；模型答错或基础设施错误不能当作容量限制。先行 64/64 正确性资格集不能替代完整矩阵。独立确认使用已冻结门槛，不重新拟合；还须核验 baseline 至少一项冻结性能门槛未通过，以证明优化对照具有区分度。这不改变独立“模型输出正确性”5 分项的 ≥95% 成功率、≥90% 正确率门槛；吞吐与延迟门槛及确认状态以顶部“当前性能验收配置”为准，只有完成标定和独立确认的配置才能正式评分。

性能验收必须包含四组完整目标：short（512 输入 token）的并发 8、16，以及 long（1024 输入 token）的并发 8、16。每组都需同时给出并检查有效输出 token/s、TTFT/TPOT/E2E p95、质量 goodput、SLO 达标比例、成功率与正确率；不能删除较难的一组来发布门槛。并发 1、4 的完整测量仍保留作基线分析。

第一次标定只产生候选数字。候选配置冻结后，必须在新的干净 Daytona 环境上做一次独立完整复测，使用不同于标定的数据与运行记录；不能以拟合门槛时使用的同一批记录自证通过。正式评分须有匹配冻结配置的独立确认记录。未确认的候选配置不能计为正式性能通过，缺失阈值也不能按默认值补齐。

平台内标为“验收阈值复测（临时评分）”的报告，只显示内部诊断分数、完整的 95/5 项目和原始测量，不构成正式最终成绩。即使临时各项通过或已经记录人工 5 分，也不把它变成正式总分。候选配置确认并发布后，新的正式评测使用该版本验收标准；历史诊断报告保留临时标记。

### Agent 父子账本与真实部署审计

`POST /agent/run` 的成功响应必须返回 `X-Request-ID`，关联本次唯一父账：`route=/agent/run`、`parent_request_id=null`。父账的 input_tokens、output_tokens、cost_micro_usd 均为 0，避免重复统计模型费用。每次真实模型调用各生成一条独立子账：`route=/agent/model_call`、`parent_request_id=父账 request_id`；至少两次调用（规划与最终回答），不能用静态答案替代调用。父子账都归属调用者的 tenant_id、key_id 和指定 model。

响应 `usage.model_calls` 必须等于子账条数，`usage.completion_tokens` 等于全部子账 output_tokens 之和。每条子账保存调用时不可变的 pricing_version，费用按该版本输入/输出单价计算；用户已用 tokens、总费用和余额变化必须与子账汇总一致，完成后预占金额与 tokens 均释放为 0，不能改动另一用户账本。Agent 的重复 `Idempotency-Key` 请求返回 409，不能再次调用模型、生成账目或重复扣费；此规则比通用生成接口允许重放已存响应的规定更严格。

`GET /admin/usage` 与普通 key 的 `GET /v1/usage` 返回的每条账目均须包含 `route`、`parent_request_id`（无父账时为 null）。普通 key 的用户身份只能来自服务端鉴权，不能由请求参数覆盖。

真实 SGLang 部署还测试普通 key 调用以下 7 个管理写路由：`POST /admin/tenants`、`PATCH /admin/tenants/{tenant_id}`、`POST /admin/tenants/{tenant_id}/credits`、`POST /admin/tenants/{tenant_id}/keys`、`POST /admin/keys/{key_id}/rotate`、`POST /admin/keys/{key_id}/revoke`、`PUT /admin/pricing`。全部须返回 401 或 403，且管理状态、密钥、价格和目标用户账本保持不变；先修改再返回拒绝也视为失败。

真实流式/非流式计费审计会用固定 tokenizer 独立精确计算包含 chat template 的输入 tokens。输出部分使用可见文本重新分词后的保守范围检查，再核对服务 usage、价格版本与账本一致性；这不是对引擎实际生成 output token IDs 的精确独立审计。Agent 子账验证调用关联、用量汇总和计费一致性，同样不宣称独立精确验证引擎输出 tokens。不要将这些账务检查与性能压测的可见输出 token/s 统计混为一谈。

以上检查并入既有 credentials 15 分的密钥生命周期与隔离、用量计费分组，不新增权重。15 项 CPU fixture 黑盒检查仍须同时通过对应真实 SGLang 部署门槛才保留组分；CPU fixture 不用于 GPU 吞吐验收，Agent 功能本身仍按原 5 分项目评分。

## CPU 软评测、GPU 正式评测与项目助教（OpenLabs）

项目成员使用正式版 **OpenLabs**，项目代号为 `LLM-server`。安装和更新命令见实验页面的“MCP插件”。`openlabs-test` 仅供内部测试，不用于项目提交。

先用 CPU 软评测发现接口与工程问题，再提交 GPU 正式评测。两个入口使用不同资源与证据，不能相互替代：

| 入口 | 执行位置与触发 | 结果与边界 |
| --- | --- | --- |
| `evaluate LLM-server --soft` | GitHub Actions 临时托管 Ubuntu CPU runner；手动触发已安装的工作流 | 18 项接口诊断，不产生官方分数，不启动 GPU，不测性能或模型能力 |
| Git push 自动软评测 | 仓库加入 `.github/workflows/llm-soft.yml` 并启用 Actions 后，每次 push 自动执行同一 CPU 工作流 | 便于快速修复；失败不会自动申请 GPU 或进入正式队列 |
| `evaluate LLM-server --formal` 或页面“评测” | 平台既有 Realtime 事件驱动队列；以绑定仓库和完整 40 位提交 SHA 创建独立 Daytona GPU 环境 | 按当前任务书自动 95 分 + 项目验收复核 5 分；仅在主动提交后执行，不因 push 自动运行 |
| `assistant LLM-server` | OpenLabs 项目助教，结合当前任务书、公开参考源码、本人的正式结果及提供的本地软评测报告 | 解释需求与原理、定位问题并建议下一步；不读取他人报告、不代提交或修改分数 |

以上 `evaluate` / `assistant` 是插件对话命令，不是需要在 Linux shell 直接执行的系统程序。先在正式项目页面完成平台登录与仓库绑定，再使用相应入口。正式提交要求完整 40 位 SHA，不能用分支名或缩写替代；平台校验绑定仓库、本人权限、配额和当前运行状态。重复 push 或打开报告不会申请 GPU。

插件命令可明确指定仓库与提交，避免误用当前目录的 origin/HEAD：

```text
evaluate LLM-server --soft --repo owner/repo --commit <完整40位SHA>
evaluate LLM-server --formal --repo owner/repo --commit <完整40位SHA>
assistant LLM-server 请结合我的软评测报告解释 SSE 为什么未通过
lab-evaluate LLM-server result <返回的运行ID或待查询句柄>
```

soft 可另外指定 `--ref main`（使用工作流所在 ref）；省略仓库、SHA、ref 时，插件仅只读解析当前 Git origin、HEAD 与分支，不替你提交代码。formal 不接受 ref，只提交已 push 的完整 SHA，且指定仓库须与平台已绑定仓库相同。软评测标识为 GitHub 运行 ID 或待查询句柄，正式结果使用平台运行 UUID，两类结果不可混用。

## 服务接口

除 `/healthz` 外全部要求 `Authorization: Bearer <API_KEY>`，缺少或错误 key 返回 401/403。API 密钥只授权本次模型服务，不授予 Daytona、数据库或平台管理权限。

### GET /healthz

就绪：HTTP 200 `{"status":"ready"}`。引擎或模型未就绪：HTTP 503。不能在后台仍下载模型时提前返回 ready。

### GET /info

```json
{"contract":"llm-lab/1.0","model_id":"Qwen/Qwen2.5-7B-Instruct","model_revision":"a09a35458c702b33eeacc393d103063234e8bc28","engine":"sglang","engine_version":"<锁定且实际运行的版本>","profile":"baseline","config":{"max_running_requests":1,"context_length":4096,"dtype":"bfloat16"}}
```

这些字段是研发工程师声明；平台会保存，项目负责人结合源码核对。禁止返回密钥。

### GET /v1/models

OpenAI 兼容 `{"object":"list","data":[{"id":"Qwen/Qwen2.5-7B-Instruct","object":"model"}]}`。

### POST /v1/chat/completions

支持 `model, messages, temperature, max_tokens, stream, stream_options.include_usage, response_format`。本轮性能请求的 `response_format={"type":"json_object"}` 必须原样转发至 SGLang，不得丢弃、事后修补 JSON 或替换模型输出。实现 stream=false 的 `choices[0].message.content` 和 stream=true 的 SSE：非空 `choices[0].delta.content`、结束 `finish_reason`、真实 tokenizer 的 `usage.completion_tokens`、最终 `data: [DONE]`。role/空事件不算首 token；SSE 包数不是 token 数。

错误有明确 HTTP 状态。处理客户端取消、超时、并发限制；项目负责人检查取消是否传递到引擎而不是只关闭前端连接。

### POST /agent/run

成功响应返回 `X-Request-ID`；父账与每次模型调用的子账按下文“Agent 父子账本与真实部署审计”关联，重复 Idempotency-Key 返回 409。

输入：

```json
{"task":"Where is order A20417? Return order_id, status and eta_days.","tool_data":{"orders":{"A20417":{"status":"shipped","eta_days":3}}}}
```

输出：

```json
{"answer":{"order_id":"A20417","status":"shipped","eta_days":3},"tool_calls":[{"name":"lookup_order","arguments":{"order_id":"A20417"}}],"usage":{"model_calls":2,"completion_tokens":48}}
```

必须实际经过模型规划、工具分发、模型最终回答。仅允许白名单工具 `lookup_order`，工具数据按请求提供，不执行用户提供的 shell。测试器随机化订单 ID 和事实；自动项检查答案和轨迹结构，源码真实性归项目验收复核。


### GET /metrics

Bearer 鉴权，至少返回 `active`、`queued` 与 `counters.abort_acknowledged`（引擎确认取消的累计次数），并记录 completed/rejected/cancelled/timed_out 等请求状态。`/info.config` 必须声明整数 `gateway_slots`（1–64）和 `gateway_queue`（0–112），二者总和 ≤120。队列满返回 429，并带 Retry-After。

字段语义和计数重置时机写入 README。平台执行并发突发、断开响应流、等待 active/queued 归零，再发正确性请求验证恢复；取消确认计数应增加。这些计数是服务声明，不能单独证明 GPU 计算已停止；日志与引擎请求 ID 必须可追溯。平台不会把这些工程探针混进正常性能测量窗口。


## SSE 流式输出：原理、实现与测试

### 背景：为什么回答能逐步出现？

大模型通常按自回归方式逐步生成 token：`y_t ~ P(y_t | 输入, y_1, …, y_(t-1))`。token 是模型的文本单位，不一定对应一个字或词。非流式接口把生成内容攒齐，最后返回一份 JSON；流式接口将已生成的内容及时发给客户端。不能先生成完整答案，再用 sleep 分块发送来模拟流式输出。

```text
非流式：问题 → 生成第 1、2、3…个 token → 完成 → 一次返回完整 JSON
流式：  问题 → 生成一段 → 发送 → 生成下一段 → 发送 → … → 结束
```

**SSE**（Server-Sent Events，服务器发送事件）是传输格式，不是模型生成算法。同一次 HTTP 请求保持连接，服务端持续追加事件；客户端不需要轮询，也不需要每个 token 重新发请求。本项目用带 Bearer 鉴权的 POST 请求，返回 `Content-Type: text/event-stream`；浏览器应使用 fetch 的响应流或兼容 SDK，不能直接用只支持 GET 的原生 EventSource 替代这个 POST 接口。

SSE 让用户更早看到内容，但本身不保证模型总生成时间缩短。一个事件可能合并多个 token；一个网络读取块也可能包含半个或多个事件，两者都不能直接当成 token。

### 实现链路：两端都要开启 streaming

```text
本地 Agent / 测试客户端
  POST /v1/chat/completions，stream=true
       ↓ Bearer 鉴权 → 有界排队 → 分配同一个请求 ID
你实现的 Python 网关（8000 端口）
  向 SGLang 发起 stream=true，并以流方式读取 HTTP 响应
       ↓
SGLang（内部端口）逐步推理、输出增量事件
       ↓
网关收到事件 → 校验并 yield → SSE 响应 → 客户端拼接 delta.content
       ↓
finish_reason → usage（请求 include_usage=true 时）→ [DONE] → 关闭连接、释放名额
```

服务对外只开放网关；引擎管理接口保持内部访问。参考实现中 `server/backend.py` 负责向 SGLang 发起流式请求，`server/streaming.py` 负责解析和校验，`server/app.py` 通过 FastAPI 的 StreamingResponse 转发。任务目录中的 `server/engine.py` 可以承担 backend.py 的职责，文件名可调整。

下面只展示核心机制，不是可以替代完整网关的代码。`client` 为复用的 httpx.AsyncClient，`relay` 为你的 SSE 解析与校验器；实际实现还须加入鉴权、准入控制、超时、异常处理和取消传播。

```python
# 1. 告诉引擎生成流式结果，并避免 HTTP 客户端先把响应读完。
request = client.build_request("POST", "/v1/chat/completions", json={
    **payload,
    "rid": request_id,
    "stream": True,
    "stream_options": {"include_usage": True},
})
upstream = await client.send(request, stream=True)
upstream.raise_for_status()  # 实际实现须保证错误路径也关闭 upstream

# 2. 边读边转发；不要 await upstream.aread() 或先拼接完整答案。
async def generate():
    try:
        async for event in relay(upstream, deadline):
            yield event
    finally:
        await upstream.aclose()
        # 实际实现：释放请求槽位；非正常完成时取消对应引擎请求。

return StreamingResponse(generate(), media_type="text/event-stream", headers={
    "Cache-Control": "no-cache",
    "X-Accel-Buffering": "no",
})
```

`stream=true` 是发给引擎的生成参数；`client.send(..., stream=True)` 是 HTTP 客户端的读取方式，两者缺一都可能导致等待完整响应。响应头只是防缓冲提示，仍须实测公网代理是否及时转发；不要收集完整响应后再返回，也不要用响应压缩或代理缓冲把事件攒到最后。

### 事件格式与生命周期

本项目每个 JSON 事件使用一行 `data: <JSON>`，后接一个空行，即 `\n\n`。下方省略 id、model 等字段，只说明增量字段和结束顺序；示意文字分块不代表真实 tokenizer 的切分，usage 数字也只是格式示例，实际必须来自引擎。

```text
data: {"choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":"北京"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":"是中国的首都。"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"choices":[],"usage":{"prompt_tokens":12,"completion_tokens":6,"total_tokens":18}}

data: [DONE]

```

客户端只拼接非空 `choices[0].delta.content`。role、空 delta、usage 都不算输出内容；遇到 `[DONE]` 才确认协议正常结束。`finish_reason=length` 表示达到长度上限，不等于回答一定完整或正确。流结束但缺少 finish_reason、请求的 usage 或 `[DONE]` 应按异常处理，不能伪装成功。

在响应头发出前，鉴权失败返回 401，队列满返回 429，未就绪/超时按合同返回对应错误。HTTP 200 和响应头已经发出后，不能再把状态码改成 500：应发送明确的流内 error 事件并结束，不补造 `[DONE]`。客户端必须检查 error，不能只看 HTTP 200。

客户端断开时，网关要关闭上游连接、释放 active/queue 名额，并使用提交给 SGLang 的同一个请求 ID 取消引擎任务。仅停止网页显示或关闭 HTTP 读取，不足以证明 GPU 已停止生成；取消、超时、异常路径都需要清理，且不能重复释放名额。

## 多用户 API Key、用量与计费管理服务

### 背景与目标

一个共享 API_KEY 只能回答“请求是否知道这串密钥”，无法区分是谁调用、花了多少、额度是否足够，也无法只撤销某个用户的访问。你需要把模型服务交付成一个可供多个用户或 Agent 使用的小型模型 API 平台：推理网关之外，还要有自己的管理服务、管理网页和持久化账本。

此处有两个不同的 token：

- API Key / access token：调用凭据。客户端在 `Authorization: Bearer <key>` 中提交，用来确定用户、权限和额度。
- 模型 token：模型处理的输入/输出文本单位。它们是用量与计费依据，不是访问凭据。

本项目要求多用户 API 的凭据和用量能力，不要求复制某个商业产品的订阅模式。第一期实现内部余额、计费与账单，不要求真实收款、信用卡、税务或支付渠道；界面明确标注“实验账本”，不能把它与平台租用 Daytona 的真实预算混为一谈。

### 必须交付的管理网页与后台

管理网页入口为 `GET /console`，可使用简单 HTML 或任意前端框架；必须连接真实管理 API 和持久化数据库，不能只有截图、mock 页面或直接编辑 JSON 文件。至少完成以下操作：

| 模块 | 必须实现 | 完成标准 |
| --- | --- | --- |
| 用户/租户 | 创建、列出、停用用户，设置余额和请求额度；最少 Alice、Bob 两个独立用户 | 同一模型服务中两个用户的用量、额度、账单互不混淆 |
| 密钥管理 | 同一用户多把 key；创建、命名、查看状态/到期时间、轮换 rotate、撤销 revoke | 原文仅创建/轮换时展示一次；列表只有 key_id、前缀/尾号和状态 |
| 权限隔离 | 管理员凭据与推理 key 分离；普通 key 只能推理和读取自己的使用情况 | A 的 key 不能查看 B 的账单、创建用户、充值或调用引擎管理接口 |
| 用量统计 | 按用户、key、模型、日期统计请求数、输入/输出 tokens、失败/取消数 | 同时保存逐请求账本和汇总，汇总可与明细对账 |
| 定价与账单 | 输入与输出 token 单价分别配置；每条账目保存价格版本和金额 | 正常流式与非流式均按真实用量结算；更新价格不重算历史账目 |
| 额度与限流 | 用户余额、累计 token 上限、RPM、并发上限；余额不足在进入引擎前拒绝 | 多请求并发不会透支；限流不能通过多建一把 key 绕过用户级总限额 |
| 审计与持久化 | 创建/轮换/撤销/充值操作审计；进程重启后保留用户、key 摘要、余额与账单 | setup.sh 幂等重跑不清空数据库；日志不出现完整密钥 |

RPM 是 Requests Per Minute（每分钟请求数），与同时在途的并发数不同。普通推理调用自动识别身份，不让客户端用 `user_id`、`tenant_id` 或 `role` 指定计费归属。

密钥使用密码学安全随机数生成（至少 32 个随机字节），数据库保存校验摘要，不保存可回读的原文；可使用 HMAC-SHA256，并把服务端 pepper 放在独立私密环境变量中。不能把 pepper、管理员凭据、已签发 key 放入 GitHub、前端构建产物、URL 或日志。若使用管理员网页登录会话，设置安全 Cookie、过期时间并保护写操作免受 CSRF；普通 key 不得获得管理能力。

### 请求与计费实现流程

```text
Agent 携带自己的 API Key
  → 网关校验 key 状态/有效期 → 服务端确定 tenant_id + key_id
  → 检查用户状态、RPM、并发、余额、token 上限
  → 数据库事务：创建请求记录并预占最大允许费用/用量
  → 提交给 SGLang（仍使用同一个请求 ID）
  → 非流式或 SSE 输出；从引擎记录实际 input/output tokens
  → 事务结算一次：扣实际金额、释放未使用预占、更新汇总
  → 管理网页展示账单；用户 API 只能返回自己的用量
```

使用可信引擎的 usage，输入包含实际 chat template；服务端计费不接受客户端提交的 `usage`、`cost` 或 `user_id`。即使客户端不请求 `stream_options.include_usage`，网关也必须自行取得计费数据。模型前缀缓存命中不代表用户输入 token 自动为零；第一版统一按输入/输出 token 价计费，cached_tokens 单独记录，不能暗中更换计价规则。性能评测中控制端的独立 tokenizer 复核是另一项验证，不等于允许客户端决定账单。

金额使用整数微美元（1 USD = 1,000,000 micro-USD）或精确 Decimal，不用二进制浮点累计余额。以下单价仅为确定性测试夹具，不是模型市场报价或真实收费承诺：输入每 token 2 micro-USD，输出每 token 6 micro-USD。

```text
cost_micro_usd = input_tokens × 2 + output_tokens × 6
例：输入 100、输出 50 → 100×2 + 50×6 = 500 micro-USD = 0.0005 USD
```

预占按已验证的输入 token 数和本次允许的 max_tokens 上限计算，成功后按实际用量结算并返还差额。余额检查与预占必须在同一个数据库事务中执行；不能先读余额、稍后异步扣费。SQLite WAL + 事务可满足本项目单机实现，不强制 Redis、外部数据库或微服务拆分；多进程部署时仍要验证事务与锁的边界。

每个请求使用服务端唯一 request_id；内部重试、重复结束事件不能重复扣费。对显式提供 `Idempotency-Key` 的生成请求，实现按租户、路由和请求体哈希去重：同 key 同请求不能重复推理或扣费；同 key 不同请求体返回 409。重复进行中的请求可返回 409 `request_in_progress`；已完成请求可返回已保存结果或 409 `request_already_completed` 和原 request_id，但不可悄悄再生成一次。未提供幂等键的独立调用按独立请求处理。

| 生命周期 | 账本与额度要求 |
| --- | --- |
| 鉴权失败、未进入引擎的拒绝 | 不扣模型费用，不产生已结算 token 用量 |
| 正常完成 | 按实际 input/output usage 结算一次，释放多余预占 |
| 客户端断开/超时 | 传播取消、关闭流；若取得可信实际 usage，按截止取消的实际用量结算 |
| 中断且未取得完整 usage | 标记 pending_reconciliation（待对账），保留已预占额度，不能伪造 0 token、默默收满上限或假装结算成功 |
| 重启恢复 | 扫描未完成账目，对已终止任务核对引擎证据；模拟故障测试在恢复后 60 秒内收敛，不能重复扣费或永久冻结余额 |
| 撤销/过期/轮换 | 操作完成后发起的新请求立即按新状态鉴权；已获准的在途请求可完成，按原用户和 key_id 记账，规则写入 README |

第一期统一采用零宽限期轮换：原子创建新 key、撤销旧 key；新 key 可用，旧 key 后续请求返回 401。正常会话中已获准请求的处理规则如上。恢复时若无法取得可信用量，必须保留失败证据并以可审计的 credit_adjustment 释放预占，记录未计费用量/金额状态为 unknown，不能把未知值写成真实 0；账本明确显示该次未完成精确计费。

### 固定接口合同 credential-service/1

所有管理 API 在同一个网关下提供，仅接受独立 ADMIN_API_KEY（或由它建立的管理会话）。普通 API Key 不得调用 `/admin/*`。创建资源返回 201，查询/轮换/撤销/调整余额成功返回 200；错误使用 `{"error":{"code":"...","message":"..."}}`，不泄露密钥。时间使用 UTC ISO 8601，金额/额度使用整数。

| 接口 | 请求与返回最小约定 |
| --- | --- |
| `POST /admin/tenants` | 输入 name、balance_micro_usd、token_limit、rpm_limit、concurrency_limit；返回 tenant_id 与设置 |
| `GET /admin/tenants` | 返回 items 数组，含 tenant_id、name、status、余额、已用与预占 tokens |
| `PATCH /admin/tenants/{tenant_id}` | 修改 status（active/disabled）和限额；余额由单独调整接口修改 |
| `POST /admin/tenants/{tenant_id}/credits` | 输入 delta_micro_usd、reason 与 Idempotency-Key；返回 adjustment_id 和余额；重复同请求不重复入账，不能扣出负可用余额 |
| `POST /admin/tenants/{tenant_id}/keys` | 输入 name、expires_at；返回 key_id、api_key（仅这一次）、status、expires_at |
| `GET /admin/tenants/{tenant_id}/keys` | 返回 items，含 key_id、masked_key、status、created_at、expires_at；禁止 api_key 原文 |
| `POST /admin/keys/{key_id}/rotate` | 输入 expires_at；返回新 key_id、api_key、replaced_key_id、旧 key 的 revoked 状态 |
| `POST /admin/keys/{key_id}/revoke` | 撤销，重复撤销幂等；返回 key_id、status=revoked |
| `GET /admin/usage?tenant_id=...&from=...&to=...` | 返回 summary 与按 cursor 分页的 items：request_id、route、parent_request_id（无父账时 null）、tenant_id、key_id、model、status、input_tokens、output_tokens、cost_micro_usd、pricing_version、时间；待对账字段为 null 并带状态 |
| `GET /admin/pricing` / `PUT /admin/pricing` | 读取/设置模型的 input_micro_usd_per_token、output_micro_usd_per_token；每次更新产生不可变 pricing_version |
| `GET /v1/usage` | 普通 key 读取服务端识别的自身用户 summary：balance_micro_usd、reserved_micro_usd、input_tokens、output_tokens、cost_micro_usd；不得接受其他用户 ID 越权查询；items 账目包含 route、parent_request_id（无父账时 null） |
| `GET /console` | 真实后台页面，提供上述用户、key、余额/配额、定价、账单与审计操作；无管理身份不返回敏感数据 |

不存在或不属于可访问范围的资源不能泄露内容。无效、过期或撤销的 key 返回 401；租户停用返回 403；余额或累计 token 额度不足返回 402 `insufficient_quota`；RPM/并发超限返回 429 并附 Retry-After。仅允许明确声明的可编辑字段，客户端不能写入 used_tokens、cost、key_hash 或管理员角色。

setup.sh 增加读取 `ADMIN_API_KEY`、`KEY_HASH_SECRET`、`DATA_DIR`；首次初始化迁移与管理员入口，缺少管理配置时管理接口关闭并给出清晰提示，不能采用公开默认密码。保持原 `API_KEY` 兼容：把它初始化为一个独立的 benchmark 用户推理 key，普通权限且仍走记账/限流，不作为管理员或“免计费后门”。压测时预置足够余额和限额，单独测试配额拒绝，不能让意外余额耗尽污染性能结果。

正常进程重启或同目录 setup 重跑必须保留 DATA_DIR；Daytona 沙箱销毁会清空本地数据。仓库保存迁移、schema 和合成 seed，不能把真实用户账本/凭据提交到公开仓库；新沙箱从代码重建服务，可通过脱敏数据验证恢复流程。

#### 启动、停止与崩溃恢复入口

`setup.sh` 除正常 SGLang 启动外，必须支持 `bash setup.sh --contract-test`。此模式**只替换模型引擎**，实际用户鉴权、密钥摘要校验、租户隔离、限流、余额预占、用量账本、结算和持久化必须使用与正式服务相同的实现。不得识别评测请求返回特制答案、跳过计费，或把 contract-test 视为免鉴权后门。

| 变量 / 文件 | 约定 |
| --- | --- |

`bash setup.sh --stop` 只停止自己启动的网关/服务进程，不清空 `DATA_DIR`，不终止平台 fixture；禁止按端口或进程名批量杀掉其他进程。正式模式仍启动真实 SGLang，不把 fixture 当成 GPU 部署。

fixture 的 `POST /tokenize` 返回 `count=100`（并提供 token ID 数组）；推理返回受控的 `usage`：输入 100、输出 50。初始输入/输出价格分别为 **2 / 6 micro-USD/token**，一次费用为 `100×2+50×6=500 micro-USD`。fixture 可延迟响应、在 usage 前中断、或先发最终 usage 再延迟 `[DONE]`。这些确定性数据只用于事务验收，不用于性能分或真实模型正确性评分。 fixture 提供 `GET /health`、`GET /v1/models`、`POST /tokenize`、`POST /v1/chat/completions` 和 `POST /abort_request`（使用对应请求的 `rid`）。`/__fixture/*` 仅供控制端配置和观察，提交服务不能依赖这些管理接口或获取 fixture 管理凭据。

#### 与真实 SGLang 部署联合验收

15 项 CPU 确定性检查不是独立的模拟项目。每个 5 分组还必须通过对应的 **optimized 真实 GPU 服务部署检查**才保留该组 CPU 得分；对应部署检查失败或未完成，该组为 0，并标注“部署未验证”。原始 CPU case 结果仍保留用于定位问题，不把其通过状态改写成已获得最终组分。

真实服务检查会创建两个独立用户，分别完成流式和非流式调用，核对首个内容事件、流结束标记、实际 usage 与费用/用户账本及互不可见；测试轮换后旧 key 401、新 key 可调用；并确认原 `API_KEY` benchmark 用户的 `/v1/usage` 中已有真实模型调用账目。正式性能、正确性与 Agent 测试不能绕开鉴权、配额和账本。

#### 报告中的通过、失败与未执行

`report.checks` 的 `id="credentials"` 项上限 15，`subchecks` 三组为 `key_lifecycle`、`metering_billing`、`quota_recovery`，每组上限 5。`cases` 按上述 test_id 保存 `id/title/group/executed/passed/detail`，不包含原文 key。

`executed=true` 且 `passed=true` 才是该项通过；执行后断言失败显示未通过。`executed=false` 或缺少记录显示未执行/无记录，并列出原因。未实现 `--contract-test` 或提交服务启动失败属于未完成交付，可得 0/15，不会因显示未执行而自动免扣分；控制器自身异常或失租的报告由平台标明中断，不能据此声称正式验收通过。公开自测只产出本地证据，不能提交分数或代替控制端测试。

## 性能指标与达标规则总表

你交付的性能结果必须回答三个问题：每秒能提供多少有效输出 token、用户等待多久、在多少并发请求下仍然稳定。不能只提交 GPU 利用率截图、单个请求的速度或一个平均 token/s 数字。

### 固定测试条件

- 硬件：单张 Daytona RTX 4090；模型 Qwen/Qwen2.5-7B-Instruct，BF16，revision 以验收配置为准。
- baseline 与 optimized 分别测试 short/long 两种负载；输入长度是套用 chat template 后的 512/1024 tokens，输出上限分别为 96/384 tokens。上限不是实际输出长度，不能用上限代替实际 token 数。
- 并发档位 C=1、4、8、16；每档每种负载重复 3 轮，每轮 16 个请求。两种配置共 768 个正式测量请求，预热另外记录。
- 先通过 HTTP 网关、鉴权和真实 SSE 链路再测量；模型、采样策略、输入集合和正确性检查保持一致。不能绕过自己交付的服务去测引擎裸接口。
- 正式性能评分针对 optimized 的四组：short×8、short×16、long×8、long×16；其余档位和 baseline 用于对照与容量分析。

### 必须提交的性能表

| 指标（全称） | 单位与计算方式 | 达标方向与当前状态 |
| --- | --- | --- |
| 有效输出吞吐（Output Token Throughput） | token/s；正确且成功请求的实际输出 token 总数 ÷ 整组测量窗口秒数 | 越高越好；四组最低值以顶部“当前性能验收配置”为准 |
| TTFT（Time To First Token，首 token 延迟） | ms；发出请求至首个非空内容事件，报告 p50/p95；包含排队与网络 | 越低越好；四组 p95 上限以顶部“当前性能验收配置”为准 |
| TPOT（Time Per Output Token，平均每输出 token 时间） | ms/token；(最后内容时间−首个内容时间)/(实际输出 tokens−1)，报告 p50/p95；需多个内容事件和 N>1 | 越低越好；四组 p95 上限以顶部“当前性能验收配置”为准 |
| E2E（End-to-End Latency，端到端延迟） | ms；请求发出至完整响应结束，报告 p50/p95 | 越低越好；四组 p95 上限以顶部“当前性能验收配置”为准 |
| Goodput（满足质量与 SLO 的有效请求吞吐） | 请求/s；正确且成功、同时满足 TTFT/TPOT/E2E 上限的请求数 ÷ 测量窗口 | 越高越好；没有冻结 SLO 时不可计算验收 goodput |
| SLO 达标比例（Service Level Objective Attainment） | %；正确且成功且满足联合 SLO 的请求数 ÷ 全部请求数；失败也在分母中 | 四组最低比例以顶部“当前性能验收配置”为准，不单独生成分数 |
| 请求成功率（Success Rate） | %；正常完成协议的请求数 ÷ 全部请求数，429、超时、截断流均计失败 | 现行正确性项 ≥95%；正式性能目标每组 ≥99%（48 请求须 48/48）；标定/确认资格另要求 100% |
| 输出正确率（Quality Rate） | %；正确且成功请求数 ÷ 全部请求数，按固定任务核对答案 | 现行正确性项 ≥90%；正式性能目标每组 ≥99%（48 请求须 48/48）；标定/确认资格另要求 100% |
| 可持续并发（Sustainable Concurrency） | 同时在途请求数；测试档位中仍满足全部质量、吞吐与延迟门槛的最大 C | 必须测到 C=16；“发出了 16 个请求”不等于“并发 16 达标”；无门槛时不宣称可持续并发 |
| 显存与容量 | MiB/GiB；报告进程峰值显存、KV token 预算、active/queued 峰值；区分 allocated/reserved 与整卡占用 | 目标负载无 OOM；配额、队列有界；取消后请求与 KV 生命周期结束，不要求缓存内存池退还全部显存 |
| 部署与恢复 | 秒；首次 setup 就绪时间、幂等重跑、取消后恢复请求结果 | 安装就绪预算 ≤900 秒；同配置重跑不产生重复引擎；取消后能继续服务 |

p95 表示 95% 样本不超过该值。不要把所有并发/长短请求混成一个 p95 来掩盖某组失败。每组保留成功数、错误分类、原始到达时间、实际输出 tokens 和至少三轮记录；正式报告现有字段以 p95 为主，p50 可随工程压测结果提交。

“token 的并发量”应拆成 C（同时在途请求）、token/s（吞吐）和 KV token budget（缓存容量）三个量。ITL（Inter-Token Latency，相邻 token 间隔）只有真实逐 token 时间戳才能计算；SSE 事件间隔只作为块间隔诊断，不冒充 ITL。

## 性能验收工作负载

性能验收针对最终 HTTP 服务，不是只检查实验文件是否存在。平台固定 RTX 4090、Qwen/Qwen2.5-7B-Instruct revision `a09a35458c702b33eeacc393d103063234e8bc28`、BF16、上下文上限和负载版本。模型变小、换精度、缩短要求的输出或调用外部 API 都不属于合法优化。

平台比较 baseline 和 optimized，并记录每档并发的成功/失败、正确性、TTFT、E2E、TPOT、输出 token/s、goodput。服务接口、输出正确性和 Agent 项只验收最终 optimized 服务；正确性分母包含该服务全部测试请求及失败。baseline 是重建与性能负对照，失败仍保存，但不混入最终服务正确性分母。独立预热，不把预热请求算入计分窗口；保留超时和失败；共享前缀与不同前缀、冷缓存与热缓存分开记录。两种配置使用同一批测试输入。输出 token 数由控制端使用指定 tokenizer 对可见输出文本重新计数，不直接相信服务自报 usage；该数字不包含隐藏 token，也不假装是引擎内部 token 时间戳。

- **并发**：同时在途的请求数；不是 token/s。可持续并发是保持成功率、正确性和延迟 SLO 的最大测试档位。
- **输出吞吐 output token/s**：正确且成功的输出 token 数除以整个测量窗口。输入 token 不混入输出吞吐；全部成功输出吞吐另作诊断，不用错误答案换取速度分。
- **TTFT（Time To First Token）**：请求发出至第一个非空输出内容事件。
- **E2E（End-to-End Latency）**：请求发出至完整响应结束。
- **TPOT（Time Per Output Token）**：首个至最后输出内容事件时间除以输出 token 数减一，是每个请求的平均解码时间代理；不能替代逐 token 尾延迟。
- **ITL（Inter-Token Latency）**：相邻 token 的时间间隔。SSE 可合并多个 token，未记录独立 token 时间戳时，只能报告块间隔，不能标成 ITL。
- **SLO（Service Level Objective）**：例如 p95 TTFT 和 E2E 的明确上限。
- **Goodput**：单位时间内正确且同时满足 SLO 的请求数。输出很快但错误或超时的请求不计入。

### 硬指标配置与标定

Daytona 首轮从零验证完成后，平台发布冻结的 `acceptance.json`，包含 GPU、模型、工作负载、并发档位、请求数、输入/输出限制、最低输出 token/s 与 goodput、最高 p95 TTFT/TPOT/E2E、成功率和正确率，以及每项分数。报告保留该配置版本与实测值。

## 自动优化实验合同

平台完成服务和 Agent 测试后，在独立 GPU 上依次运行：

```bash
bash experiments/run.sh --case kv --out results/platform-<run-id>/kv
bash experiments/run.sh --case prefix --out results/platform-<run-id>/prefix
bash experiments/run.sh --case attention --out results/platform-<run-id>/attention
```

入口必须支持新的输出目录，在本次环境实际执行，不能复制已提交的结果冒充新测量。按实验用途读取模型配置与 HF_HOME：Prefix 使用服务的 MODEL_ID / MODEL_REVISION（7B），KV 使用下述独立固定的 1.5B 模型，Attention 仅生成合成张量；manifest 如实记录所用模型及实验用途。依赖由 setup.sh 安装；运行实验不临时升级环境。KV/Attention 最多各 300 秒，Prefix 最多 480 秒，并受完整评测总时限约束。实验可停止本项目服务以避免同时加载两份模型。

每项自动 10 分：执行溯源 2、矩阵覆盖 2、输入一致性 1、性能数据 1、数值/输出正确性 2、机制证据 2，逐项展示得分与理由。原理实验不要求固定加速倍数；最终服务的硬性能门槛另计入 30 分。平台不信任自报 points 或 summary.pass，也不把退出 0 当作正确性证明。

KV 数学等价性实验独立固定为 Qwen/Qwen2.5-1.5B-Instruct revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`，参考实验使用 FP32 并关闭 TF32，不加载 7B FP32。FP32 最大绝对误差 ≤0.001、top-1 一致率 100%；平台保留 BF16 对照兼容，最大绝对误差 ≤0.15、rtol=0.02、top-1 一致率 100%，不得因失败放宽容差。最终 SGLang 服务使用 7B BF16，不把 1.5B FP32 原理通过写成 7B BF16 logits 对照通过。

- KV：cache on/off × 长度 128/512 × 3 轮，共 12 条；固定回放 32 个 decode token。预热后 GPU 同步计时。相同输入与 continuation，比较逐位置 logits；记录峰值 allocated/reserved 和容量公式。BF16 最大绝对误差 ≤0.15、FP32 ≤0.001，top-1 一致率 100%，不事后放宽容差。
- Prefix：使用与最终服务相同的 7B BF16 模型及 revision；on/off × 共享/不同前缀 × 3 轮 × 8 请求，共 96 条。共享前缀 512 tokens，先清缓存再跑冷/热请求；保存输入 token IDs 和真实 cached_tokens。关闭时命中为 0，共享热请求 ≥512，冷/不同前缀 <512。原始输出必须正确，不以速度推断缓存命中。
- Attention：使用合成 Q/K/V 张量，不加载 7B 模型权重；math/flash × 长度 128/512/1024 × 3 轮，共 18 条；B=1,H=8,dh=64，BF16、causal、dropout=0，预热 5 次，每轮 10 次。相同 Q/K/V，最大绝对误差 ≤0.02，保存 profiler 算子。后端不支持应明确失败，不静默回退后宣称 flash。

数值失败仍保留完整数据并返回非零；中途失败标记 complete=false。源码、原始数据和 docs/performance.md 应可相互追溯。人工验收仍仅 5 分，不为这些实验另设人工分。

### 证据文件格式

每个 `--out` 目录必须生成 UTF-8 JSON 文件，不允许符号链接，每个被采集文件最多 256,000 字节；未完成字段写 null，禁止 NaN/Infinity。所有原始行的分组键必须唯一，缺失/重复/额外样本都会使矩阵检查失败。

`manifest.json`：`case`（kv/prefix/attention）、`time`（本次 UTC ISO 时间）、`commit`（完整 SHA）、`model`、`revision`、`gpu`（`nvidia-smi --query-gpu=name,uuid,driver_version,memory.total --format=csv,noheader` 原始文本去尾部换行）、`software`（torch/transformers/sglang 版本）、`cuda`、`complete`（只有完整运行才为 true）、`parameters`。数值不通过仍应保留 complete=true，并返回非零；中途失败为 false。

- KV parameters：lengths=[128,512]、decode_tokens=32、warmup≥1、repeats=3、dtype=bfloat16 或 float32。raw.jsonl 共 12 行：variant=cache_on/cache_off、length、repeat=0/1/2、input_hash、continuation_hash、decode_tokens、dtype、elapsed_ms、peak_allocated_bytes、peak_reserved_bytes、max_abs_error、atol、rtol、top1_agreement。同一长度的 prompt/continuation 哈希必须一致。summary.json：layers=28、KV_heads=2、head_dim=128、dtype_bytes（2/4）、KV_bytes_per_token；measurements 两项包含 length、KV_bytes_one_request、KV_bytes_eight_requests（包含额外 32 token）。逐位置比较 logits，记录全部位置最大误差；评分采用保守的最大绝对误差阈值，而不是采信自报 allclose。
- Attention parameters：warmup≥5、groups=3、iterations=10、dtype=bfloat16、causal=true、dropout=0。raw.jsonl 共 18 行：variant=math/flash、length、repeat、shape、output_shape、input_hashes（Q/K/V 三个 SHA256）、elapsed_ms、peak_allocated_bytes、peak_reserved_bytes、max_abs_error、atol=.02、rtol=.02。另存 math-128-operators.json、flash-128-operators.json 等三个长度共 6 个文件，内容是 profiler 算子名称字符串数组；保存完整 trace 供追溯。
- Prefix parameters：prefix_tokens=512、requests=8、repeats=3。raw.jsonl 共 96 行：variant=on/off、group=shared/unique、repeat=0/1/2、index=0…7、input_hash、prefix_hash、prefix_length=512、input_tokens、cached_tokens、cache_state、output、transport_ok、ttft_ms、e2e_ms。每轮 index=0 为 cold，开启缓存且共享前缀 index>0 为 hot。inputs.json 为 `{ "shared": [8个token ID数组], "unique": [8个token ID数组] }`；hash 使用 Python `sha256(json.dumps(value, sort_keys=True).encode()).hexdigest()`。每个 on/off、shared/unique、repeat 组合保存 `<variant>-<group>-<repeat>-flush.json`，至少包含 status=200。实际引擎命中计数来自服务结果，不能由速度推断。summary.json 保留各组窗口、成功率、质量 goodput；不得隐去零 goodput。

张量哈希使用连续张量原始字节的 SHA256；Prefix 使用上面的 JSON 序列化。保存原始失败记录及图表，docs/performance.md 链接同一 commit 的证据。未执行或格式错误的组不得显示“通过”。

## 候选阈值与独立确认

独立确认成功后，控制端可重新审计原始证据，另生成带完整确认凭据的 `finalized-report.json` 作为正式自动评分；原始 `report.json`、测量记录和历史临时报告不改写。仅将 provisional 改为 false 不能生效，页面还须核对确认凭据与当前运行和 commit 的绑定；人工验收仍仅 5 分。

标定数据资格与正式性能评分是两层要求：生成候选阈值和独立确认时，optimized 的 short/long × 并发 1/4/8/16 全部 8 组，以及 baseline 的 short/long × 并发 1 两组，必须每个测量请求都正确且成功（100%）；不能用其他组的高分抵消。正式性能评分目标为 optimized 的 short/long × 并发 8/16 四组，各组成功率与正确率均须 ≥99%。本期每组 3 轮 × 16 = 48 个测量请求，因此 ≥99% 实际要求 48/48 正确且成功（47/48 约为 97.92%，不达标）。baseline 的较高并发只允许已确认的容量失败，且每轮至少有 1 个正确成功样本；模型答错或基础设施错误不能当作容量限制。先行 64/64 正确性资格集不能替代完整矩阵。独立确认使用已冻结门槛，不重新拟合；还须核验 baseline 至少一项冻结性能门槛未通过，以证明优化对照具有区分度。这不改变独立“模型输出正确性”5 分项的 ≥95% 成功率、≥90% 正确率门槛；吞吐与延迟门槛及确认状态以顶部“当前性能验收配置”为准，只有完成标定和独立确认的配置才能正式评分。

### Agent 父子账本与真实部署审计

`POST /agent/run` 的成功响应必须返回 `X-Request-ID`，关联本次唯一父账：`route=/agent/run`、`parent_request_id=null`。父账的 input_tokens、output_tokens、cost_micro_usd 均为 0，避免重复统计模型费用。每次真实模型调用各生成一条独立子账：`route=/agent/model_call`、`parent_request_id=父账 request_id`；至少两次调用（规划与最终回答），不能用静态答案替代调用。父子账都归属调用者的 tenant_id、key_id 和指定 model。

响应 `usage.model_calls` 必须等于子账条数，`usage.completion_tokens` 等于全部子账 output_tokens 之和。每条子账保存调用时不可变的 pricing_version，费用按该版本输入/输出单价计算；用户已用 tokens、总费用和余额变化必须与子账汇总一致，完成后预占金额与 tokens 均释放为 0，不能改动另一用户账本。Agent 的重复 `Idempotency-Key` 请求返回 409，不能再次调用模型、生成账目或重复扣费；此规则比通用生成接口允许重放已存响应的规定更严格。

`GET /admin/usage` 与普通 key 的 `GET /v1/usage` 返回的每条账目均须包含 `route`、`parent_request_id`（无父账时为 null）。普通 key 的用户身份只能来自服务端鉴权，不能由请求参数覆盖。

真实 SGLang 部署还测试普通 key 调用以下 7 个管理写路由：`POST /admin/tenants`、`PATCH /admin/tenants/{tenant_id}`、`POST /admin/tenants/{tenant_id}/credits`、`POST /admin/tenants/{tenant_id}/keys`、`POST /admin/keys/{key_id}/rotate`、`POST /admin/keys/{key_id}/revoke`、`PUT /admin/pricing`。全部须返回 401 或 403，且管理状态、密钥、价格和目标用户账本保持不变；先修改再返回拒绝也视为失败。

真实流式/非流式计费审计会用固定 tokenizer 独立精确计算包含 chat template 的输入 tokens。输出部分使用可见文本重新分词后的保守范围检查，再核对服务 usage、价格版本与账本一致性；这不是对引擎实际生成 output token IDs 的精确独立审计。Agent 子账验证调用关联、用量汇总和计费一致性，同样不宣称独立精确验证引擎输出 tokens。不要将这些账务检查与性能压测的可见输出 token/s 统计混为一谈。

以上检查并入既有 credentials 15 分的密钥生命周期与隔离、用量计费分组，不新增权重。15 项 CPU fixture 黑盒检查仍须同时通过对应真实 SGLang 部署门槛才保留组分；CPU fixture 不用于 GPU 吞吐验收，Agent 功能本身仍按原 5 分项目评分。

本轮 V5 负载（`typed-json-numbered-records-prose-exact-input/5`）是 512/1024 个 chat-template 输入 token、并发 1/4/8/16、每格 3 轮且每轮 16 个测量请求，另有 2 个预热请求；短/长任务分别提取 1/8 条记录，最大输出分别 96/384 token。采用带共享自然语言前缀的结构化信息提取，每个 worker 完成一个请求再发下一个。这个负载用于优化对照，不代表通用聊天吞吐；运行完整矩阵会消耗 GPU 实验时间，执行前检查剩余额度。脚本在你明确执行命令时才推理，环境安装不自动跑性能测试。

输出包含每个 profile 的 `*-serving-summary.json`、`*-serving-raw.jsonl`、预热记录、每轮输入、服务声明及 benchmark manifest。比较正确率、成功率、有效 token/s、TTFT/TPOT/E2E p95；token 数由本地固定 tokenizer 独立统计，SSE 事件间隔仍不等于逐 token ITL。直接运行的 manifest 标为 `participant_cli_unattested`、`official_score=false`，可编辑的自测证据不能上传为正式成绩。当前 acceptance 状态见上方生成区块；在阈值为 null、status=uncalibrated 或尚未独立确认时，SLO/goodput 仅供分析，不能把缺失阈值当作通过。平台更新冻结配置后，应重新下载同版本 acceptance 并保存配置哈希，不混用新旧门槛。


## 候选阈值与独立确认

独立确认成功后，控制端可重新审计原始证据，另生成带完整确认凭据的 `finalized-report.json` 作为正式自动评分；原始 `report.json`、测量记录和历史临时报告不改写。仅将 provisional 改为 false 不能生效，页面还须核对确认凭据与当前运行和 commit 的绑定；人工验收仍仅 5 分。

标定数据资格与正式性能评分是两层要求：生成候选阈值和独立确认时，optimized 的 short/long × 并发 1/4/8/16 全部 8 组，以及 baseline 的 short/long × 并发 1 两组，必须每个测量请求都正确且成功（100%）；不能用其他组的高分抵消。正式性能评分目标为 optimized 的 short/long × 并发 8/16 四组，各组成功率与正确率均须 ≥99%。本期每组 3 轮 × 16 = 48 个测量请求，因此 ≥99% 实际要求 48/48 正确且成功（47/48 约为 97.92%，不达标）。baseline 的较高并发只允许已确认的容量失败，且每轮至少有 1 个正确成功样本；模型答错或基础设施错误不能当作容量限制。先行 64/64 正确性资格集不能替代完整矩阵。独立确认使用已冻结门槛，不重新拟合；还须核验 baseline 至少一项冻结性能门槛未通过，以证明优化对照具有区分度。这不改变独立“模型输出正确性”5 分项的 ≥95% 成功率、≥90% 正确率门槛；吞吐与延迟门槛及确认状态以顶部“当前性能验收配置”为准，只有完成标定和独立确认的配置才能正式评分。

性能验收必须包含四组完整目标：short（512 输入 token）的并发 8、16，以及 long（1024 输入 token）的并发 8、16。每组都需同时给出并检查有效输出 token/s、TTFT/TPOT/E2E p95、质量 goodput、SLO 达标比例、成功率与正确率；不能删除较难的一组来发布门槛。并发 1、4 的完整测量仍保留作基线分析。

第一次标定只产生候选数字。候选配置冻结后，必须在新的干净 Daytona 环境上做一次独立完整复测，使用不同于标定的数据与运行记录；不能以拟合门槛时使用的同一批记录自证通过。正式评分须有匹配冻结配置的独立确认记录。未确认的候选配置不能计为正式性能通过，缺失阈值也不能按默认值补齐。

平台内标为“验收阈值复测（临时评分）”的报告，只显示内部诊断分数、完整的 95/5 项目和原始测量，不构成正式最终成绩。即使临时各项通过或已经记录人工 5 分，也不把它变成正式总分。候选配置确认并发布后，新的正式评测使用该版本验收标准；历史诊断报告保留临时标记。



## 原理实验与服务模型分工

KV 数学等价性实验独立固定为 Qwen/Qwen2.5-1.5B-Instruct revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`，参考实验使用 FP32 并关闭 TF32，不加载 7B FP32。FP32 最大绝对误差 ≤0.001、top-1 一致率 100%；平台保留 BF16 对照兼容，最大绝对误差 ≤0.15、rtol=0.02、top-1 一致率 100%，不得因失败放宽容差。最终 SGLang 服务使用 7B BF16，不把 1.5B FP32 原理通过写成 7B BF16 logits 对照通过。

Prefix 使用最终服务的 7B BF16；Attention 使用合成 Q/K/V 张量，不加载 7B 模型权重。


## 本轮配置与验收状态

V5 只调整长任务的指令表达：输入记录逐行标为 Record 1–8，输出数组必须保持编号对应的输入顺序，不得按 city、id 或 units 分组或排序，编号不能加入输出。短任务与 V4 逐字段保持一致；严格 JSON 字段类型、值和数组顺序判定不变，不删困难样本或降低答案标准。仍使用同一自然语言前缀、7B BF16、JSON 模式与中性解码设置，输入 512/1024 tokens、输出上限 96/384 tokens。

最终服务及 Prefix 模型：`Qwen/Qwen2.5-7B-Instruct`，revision `a09a35458c702b33eeacc393d103063234e8bc28`，BF16。负载版本 `typed-json-numbered-records-prose-exact-input/5`，JSON 模式 `response_format={"type":"json_object"}`；固定 512/1024 输入 tokens、并发 1/4/8/16。先完成独立正确性资格集，再测完整矩阵并用新的独立运行确认阈值；标定与独立确认的当前状态以生成区块为准；未完成时性能 30 分待评定，不产生正式最终总分。`mem_fraction_static=0.8` 仅是参考配置，不是通过条件或性能保证。旧版 1.5B 的报告保留原模型与原评分规则，不冒充 7B 实测。

### Agent 父子账本与真实部署审计

`POST /agent/run` 的成功响应必须返回 `X-Request-ID`，关联本次唯一父账：`route=/agent/run`、`parent_request_id=null`。父账的 input_tokens、output_tokens、cost_micro_usd 均为 0，避免重复统计模型费用。每次真实模型调用各生成一条独立子账：`route=/agent/model_call`、`parent_request_id=父账 request_id`；至少两次调用（规划与最终回答），不能用静态答案替代调用。父子账都归属调用者的 tenant_id、key_id 和指定 model。

响应 `usage.model_calls` 必须等于子账条数，`usage.completion_tokens` 等于全部子账 output_tokens 之和。每条子账保存调用时不可变的 pricing_version，费用按该版本输入/输出单价计算；用户已用 tokens、总费用和余额变化必须与子账汇总一致，完成后预占金额与 tokens 均释放为 0，不能改动另一用户账本。Agent 的重复 `Idempotency-Key` 请求返回 409，不能再次调用模型、生成账目或重复扣费；此规则比通用生成接口允许重放已存响应的规定更严格。

`GET /admin/usage` 与普通 key 的 `GET /v1/usage` 返回的每条账目均须包含 `route`、`parent_request_id`（无父账时为 null）。普通 key 的用户身份只能来自服务端鉴权，不能由请求参数覆盖。

真实 SGLang 部署还测试普通 key 调用以下 7 个管理写路由：`POST /admin/tenants`、`PATCH /admin/tenants/{tenant_id}`、`POST /admin/tenants/{tenant_id}/credits`、`POST /admin/tenants/{tenant_id}/keys`、`POST /admin/keys/{key_id}/rotate`、`POST /admin/keys/{key_id}/revoke`、`PUT /admin/pricing`。全部须返回 401 或 403，且管理状态、密钥、价格和目标用户账本保持不变；先修改再返回拒绝也视为失败。

真实流式/非流式计费审计会用固定 tokenizer 独立精确计算包含 chat template 的输入 tokens。输出部分使用可见文本重新分词后的保守范围检查，再核对服务 usage、价格版本与账本一致性；这不是对引擎实际生成 output token IDs 的精确独立审计。Agent 子账验证调用关联、用量汇总和计费一致性，同样不宣称独立精确验证引擎输出 tokens。不要将这些账务检查与性能压测的可见输出 token/s 统计混为一谈。

以上检查并入既有 credentials 15 分的密钥生命周期与隔离、用量计费分组，不新增权重。15 项 CPU fixture 黑盒检查仍须同时通过对应真实 SGLang 部署门槛才保留组分；CPU fixture 不用于 GPU 吞吐验收，Agent 功能本身仍按原 5 分项目评分。

| 入口 | 执行位置与触发 | 结果与边界 |
| --- | --- | --- |
| `evaluate LLM-server --soft` | GitHub Actions 临时托管 Ubuntu CPU runner；手动触发已安装的工作流 | 18 项接口诊断，不产生官方分数，不启动 GPU，不测性能或模型能力 |

```text

evaluate LLM-server --formal --repo owner/repo --commit <完整40位SHA>
```

soft 可另外指定 `--ref main`（使用工作流所在 ref）；省略仓库、SHA、ref 时，插件仅只读解析当前 Git origin、HEAD 与分支，不替你提交代码。formal 不接受 ref，只提交已 push 的完整 SHA，且指定仓库须与平台已绑定仓库相同。软评测标识为 GitHub 运行 ID 或待查询句柄，正式结果使用平台运行 UUID，两类结果不可混用。

### setup.sh 的 CPU 模式与 18 项诊断

`bash setup.sh --contract-test` 必须安装并启动真实网关、鉴权、租户、SQLite/其他持久化账本与配额逻辑，只将模型适配到工作流已启动的 `ENGINE_BASE_URL` CPU fixture。不下载 SGLang、CUDA 运行时或模型权重，不申请 GPU，也不以 mock 鉴权、mock 账本取代正式工程逻辑。读取环境提供的 `API_KEY`、`ADMIN_API_KEY`、`KEY_HASH_SECRET`、`DATA_DIR` 和模型身份；这些均是临时测试配置，不写入报告或源码。

CPU fixture 返回固定输入 100 / 输出 50 tokens，用于检查协议与计费；这不是模型质量或吞吐数据。18 项检查包括 fixture、healthz、鉴权、models、info、metrics、Agent 请求校验、非流式、SSE、console 登录壳、价格、创建租户、签发 key、账单、管理写权限隔离、rotate、revoke、停用租户。`/info` 在这里仅验证接口和模型身份字段，不证明 SGLang 已在 GPU 部署。console 检查只验证无凭据 HTML 壳，不等于页面所有交互已测试。`GET /metrics` 必须鉴权，返回非负整数 active、queued 和 counters.abort_acknowledged。`POST /agent/run` 只检查路由存在、未鉴权请求拒绝，以及 task=null/tool_data=null 返回 400 或 422 且 CPU fixture 调用数不变；这项通过只表示 Agent 请求校验通过，不测试真实模型规划、工具执行或最终输出。

报告每项展示接口、预期行为、状态和安全错误原因：

| 状态 | 含义 | 处理方法 |
| --- | --- | --- |
| `pass` | 本项已执行且满足 CPU 协议断言 | 保留证据，继续其他项目；不能换算为正式分数 |
| `missing` | 接口返回 404/405/501，路由缺失或不支持 | 按任务书补齐路由与方法 |
| `invalid` | 接口存在，但格式、权限、SSE 结束标记或账本行为不符合合同 | 按错误代码和公开参考代码定位 |
| `blocked` | 前置条件失败、连接不可用或截止时间到，未能验证 | 先修 setup/fixture/依赖，再重跑；不能标为已通过 |

报告格式 `llm-soft-check/1`，包含兼容的内部标识 `project=project-2`（对外命令代号为 `LLM-server`）、`mode=soft`、仓库、完整提交 SHA、逐项 checks 与状态汇总，`official_score=false`。在 GitHub Actions 的 `llm-soft-report` artifact 下载报告；可将本地文件交给 `assistant LLM-server` 分析。软评测不覆盖 GPU 部署、模型正确性、Agent 模型推理、性能/SLO、完整 15 项正式凭据审计、崩溃恢复、原文密钥磁盘扫描或管理页面全部操作；未测试项明确列出，不能填成通过。
